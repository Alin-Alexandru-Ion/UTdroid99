# CityIntro Android experiment — 2026-11-03

The original 469e launcher now renders moving CityIntro scenes in an Android 15 x86-64 emulator using ARM64 translation and host GPU acceleration. A clean 12-second silent screen recording is `research/cityintro-emulator.mp4`; stills at `research/cityintro-visible-01.png` through `03.png` show different views. A later run was still active after 65 seconds, with visible rendering again after a transient black frame. No physical ARM64 phone, audio, full-intro completion, input, or gameplay has been verified. The debug app and shims remain research artifacts, not a redistributable port.

## Rendering follow-up

The independent SDL GLES probe (`-GLProbe`) measured SwiftShader ES 3.0 success and ES 3.1 `EGL_BAD_CONFIG`. Restarting the AVD with `-gpu host` instead produced a working ES 3.1 context reporting NVIDIA 617.42. The first host-GPU game run then faulted in `FOpenGLBase::CreateInmutableBuffer` at a null `glBufferStorage` function pointer; a crash trace is saved in `research/hostgpu-crash.log`. The temporary signal adapter preserves Android's crash handlers in the isolated debug process to expose such faults, changing normal engine signal handling for diagnostics.

The host GLES context did not advertise `GL_EXT_buffer_storage` even though the EXT entry point was present, so the diagnostic SDL build does not call that entry point without extension support. Its bounded compatibility fallback uses actual `glBufferData` for the observed flags `0` and `GL_DYNAMIC_STORAGE_BIT` (`0x100`), and aborts for other flags; mutable `glBufferData` storage is **not generally equivalent** to immutable buffer storage. The adapter follows the [Khronos EXT buffer storage interface](https://github.com/KhronosGroup/OpenGL-Registry/blob/main/extensions/EXT/EXT_buffer_storage.txt) only when that extension is advertised. A separate GLES test created a 256-byte shader-storage buffer, rebound it to an array-buffer target, and verified size 256 with no GL errors. The game trace showed a real 4 MiB allocation with the observed dynamic-storage flag, after which CityIntro rendered and changed between captured frames. The existing fail-fast texture-readback hooks remain unimplemented and were not observed firing in this run.

The `ExperimentalSDLActivity` now keeps the test in landscape. The previous 60-second watchdog was removed; the process remained active for more than 65 seconds. The temporary Android immersive-mode confirmation was dismissed manually on the emulator. The 12.0078-second capture contains 707 encoded video frames at 2400x1080 and has no soundtrack; it was created with `-nosound` and the emulator audio disabled. Frames at 2 and 10 seconds were checked visually and show different CityIntro scenes. Neither this short recording nor process survival proves complete intro playback, graphics correctness, stable frame rate, or broader gameplay.

Reproduction on this machine: start `Medium_Phone_API_35` with `-gpu host`, `-read-only`, `-no-snapshot` and the other options below; run the `-GLProbe` control, then `-SDL -Content` on a clean emulator. The game's private content remains inside the debug app. Captures and logs are ignored under `research/`, and the original GOTY installation remains unchanged.

## Earlier SwiftShader result

The engine's own log in ignored `research/cityintro-engine-latest.log` records `Unreal engine initialized`, `SDLClient initialized`, `Rendering initialized` (the engine's render subsystem, before hardware initialization), `LoadMap: CityIntro.unr`, `Bringing Level CityIntro.MyLevel up for play`, player possession and `Opening SDL viewport`. The original OpenGL driver loaded and attempted desktop core and ES contexts. It reported emulator SwiftShader as `OpenGL ES-CM 1.1 (OpenGL ES 3.0 SwiftShader 4.0.0.1)`, `Missing required OpenGL1/2 capabilities`, and `Unable to find supported OpenGL Context`; engine startup then exited through its error handler. This log is not proof of a rendered game frame or a functioning render loop.

SDL's normal Java bridge and surface lifecycle ran in a separate debug-only `ExperimentalSDLActivity` process and invoked the original launcher's main function on SDL's thread. SDL's Android Java classes are built from the pinned SDL2 checkout, release 2.32.10. The early research build used an SDL helper now archived locally under ignored `research/`. The current bootstrap applies `patches/sdl2/ut99-android.patch`; SDL's zlib license is retained. The diagnostic hooks `glGetTexImage` and `glGetCompressedTexImage` fail fast if called; they do not implement graphics operations.

The launcher first failed because Bionic iconv lacks Windows-1252. The experimental `load_iconv.c` supplies selected Windows-1252 to/from UTF-16LE and AArch64 `wchar_t` conversions; a synthetic Android fixture passed selected ASCII, euro, accented, output-bound, invalid-byte and incomplete-surrogate checks. It does not implement or validate all GNU iconv behavior. A file trace then showed the Linux launcher changing into `/system/bin/arm64`; the diagnostic adapter maps that exact path to the private game directory. Default configuration, the user's copied `Core.int`, and `Palettes.utx` were read successfully.

The previous aborting `_setjmp` and `__longjmp_chk` placeholders were replaced in the experimental candidate with a paired Bionic-backed buffer adapter. GNU AArch64 jump storage is 312 bytes and the NDK Bionic buffer is 256 bytes; the representations are not interchangeable with a real glibc. A versioned fixture passed selected zero, positive and negative values, buffer sentinels and a worker thread after explicit zero normalization. The independent Bionic baseline failed its zero case on this ARM-translated emulator (exit code 4); the precise reason is not established. Fortified longjmp stack-checking, signals, cross-runtime buffers, other environments and physical devices are unverified.

## Binary and loader experiments

`prepare_launcher_probe.py` verifies the original launcher SHA-256 `726b4fbeea173ce62e02a81f76638e939389e1be8b40fea88f0ac83b4d21e390` and creates a private copy with `DF_1_PIE` cleared. Its identified `main` is at offset `0x6e90`, derived from the original `_start` relocation; the host finds its load base through `__bss_start` at `0x311a8`. It never calls the original ELF `_start` or substitutes a Linux process interpreter.

The first loader attempt failed on an `R_AARCH64_TLS_TPREL64` reference to Core's `UnGuardBlockTLS::Data`. `prepare_launcher_tls_probe.py` verifies the input hash, replaces exactly 138 observed fixed TLS instruction sequences with calls through a register-preserving resolver, and disables exactly that relocation. The app checks that Bionic's lookup returns distinct addresses on two threads and that the resolver returns the correct address on the current thread. This narrowly scoped modification is not proven for all threading, signaling, context and ABI cases. The launcher probe SHA-256 is `fafd3829192f7f829c9b40bf2d7ece98439dd5de2e5a4d27e8eab67e815af0a4`. The `__libc_start_main` symbol in this private shim is intentionally repurposed for this trampoline and must never be used to run the original `_start`.

`prepare_render_probe.py` verifies original 469e renderer and IpDrv hashes, then changes four and one `STB_GNU_UNIQUE` bindings respectively to ordinary global bindings in separate private copies, allowing Bionic to load them. These changes may affect GNU symbol-uniqueness semantics and are not a production fix. Other libc, C++, synchronization, signal and graphics interfaces are provisional. Debug SDL preload reports successful `SDLDrv.so`, modified `Render.so`, modified `IpDrv.so` and `OpenGLDrv.so` loads.

## Reproduction and boundaries

From the repository root, use the configured NDK/CMake setup documented in [BOOT_PROGRESS.md](BOOT_PROGRESS.md):

1. Extract the pinned original `SystemARM64/ut-bin-arm64`, `Render.so`, `IpDrv.so`, `Default.ini`, and `DefUser.ini` from the verified patch into ignored `research/SystemARM64`, and keep the locally owned game copy in ignored `research/pc-reference`.
2. The historical run used the archived SDL helper. For the current reproducible build, use the bootstrap in `BUILDING.md`, which applies the recorded SDL patch.
3. Build `research/libc-probe-build`, `research/libdl-bridge-build`, `research/libm-bridge-build`, `research/cxx-bridge-build` and `research/sdl-soname-build` with CMake; then build `gradlew.bat --offline --no-daemon assembleDebug`.
4. Run `scripts/run_core_load_experiment.ps1 -Serial <explicit-serial> -SDL -Content` to stage the 658 MB ignored bundle into the debug app's private files and launch. Subsequent runs can omit `-Content`. The bundle combines the user's local data with matching patch packages; it and the original/modified proprietary runtime binaries are never included in the APK.
5. Inspect app-private `files/core-load/.utpg/System/UnrealTournament.log`, `files/core-load/sdl-launcher-output.txt`, and `adb logcat -s UT99Host:I SDL:V`. The saved emulator logs are ignored research files.

The latest debug APK SHA-256 is `76c221a9a90130d7e45870281912b495ee73d5a4a1cce4ae394a3e5334d0ad95`; `assembleDebug` and `zipalign -c -P 16 4` passed. The APK contains the host and synthetic fixture libraries, not the original engine, SDL native library, or user game files. The unmodified local UT installation was not changed. Distribution and runtime modification rights remain separate open gates.

Next work: provide a genuinely compatible Android graphics path and test its required functions and context capabilities; compare the renderer with a real ARM64 Android device or an emulator capable of the required ES level; validate all experimental runtime bridges as exercised; and capture actual CityIntro frames. The official Vulkan renderer is another research candidate but has substantial GNU C++ ABI dependencies and has not been loaded or tested here.
