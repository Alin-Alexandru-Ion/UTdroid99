# libc boot work — 2026-11-02

Latest 2026-11-03 follow-up: jump placeholders were replaced by a limited paired experiment and the original engine reached CityIntro level initialization. See [CITYINTRO_PROGRESS.md](CITYINTRO_PROGRESS.md); the earlier results below are historical.

Update 2026-11-03: the original 469e `Core.so` and `Engine.so` both returned from `dlopen` in the translated emulator using a separate, provisional load-only candidate. Constructors ran; engine initialization and the game did not. The earlier synthetic-only partial candidate remains separate and is not in the APK.

## Original Core and Engine load experiment

The load-only candidate adds provisional Android forwards for the previously missing Core symbols, environment snapshots, no-op/unsupported backtrace and allocation-trim fallbacks, and a dependency-shaped `ld-linux-aarch64.so.1` shim containing the stack guard expected by Core. It is **not a Linux dynamic loader**. Static inventory shows 129 of 129 Core GLIBC name/version/type entries, but does not validate implementation behavior, symbol binding, or complete library compatibility. A first actual Core attempt moved from the missing libc to the missing loader dependency; adding the loader-shaped shim allowed Core to load. Engine initially stopped at `__longjmp_chk`; after adding its other missing imports, it too returned from `dlopen`.

`_setjmp` and `__longjmp_chk` in the load-only candidate deliberately abort if called. They are placeholders, not functioning jump implementations; forwarding a GNU jump buffer directly to Bionic is unproven. Other provisional forwards include interfaces with potentially incompatible signal, threading, locale, directory, network, and time structures. The environment pointers are only snapshots, and the existing duplicate C++ RTTI limitation remains unresolved. The limited synthetic C++ exception/unwind control passed again after exporting the Engine-required C++ guard functions. This does not prove arbitrary engine code is safe.

Reproduce with `cmake --build research/libc-probe-build`, `cmake --build research/libm-bridge-build`, `cmake --build research/cxx-bridge-build`, an Android debug build, and `scripts/run_core_load_experiment.ps1 -Serial <serial> -Engine`. The script stages the hash-checked original libraries only into an isolated app-private `core-load` directory. They are not bundled in the APK. `research/engine-load-success.log` is the ignored translated-emulator evidence. `Engine.so` SHA-256 `7c08c8b166684f7a10b9b88e6bfe0aa965e982be5b9508bcf32061b1730f4853`; experimental libc `fad13f692bb43b25758e37e2ac8b4ed8b1e5f92a9d37f4f6e7452e0a700e7d4c`; diagnostic APK `cba3e7989a7a546a8c9c380a060115c074ffd1e45b2b5770025643efe98081ab`. APK build and 16 KiB zip alignment passed. Physical ARM64 behavior and engine startup remain untested.

## Original binary evidence

Pinned Core SHA-256 `f0ef4d6bd3b2bf13c4afb8e0ad0c3ea6be6a63182b9d64a67554136e03c3837d`: `llvm-objdump -d --demangle` shows `appFileIsNewer` calling `__xstat@GLIBC_2.17` with version `0` at `0xf2274` and `0xf22b4`; other call sites also use version 0. In `appInit`, wide-format call sites at `0xcfb4c` and `0xcfb74` pass flag 1 to `__wprintf_chk@GLIBC_2.17`. The referenced original format strings are `WARNING: Using system ini file: %ls\n` and `WARNING: Using user ini file: %ls\n`. These are static observations; execution and control-flow reachability are unproven.

## Version-0 stat experiment

`experiments/libc-probe/stat_probe.c` implements narrow, test-only `ut_gxstat` and `ut_gfxstat` calls. The fixed-width 128-byte AArch64 LP64 layout and accepted version 0 were derived from pinned glibc 2.31 commit `9ea3686266dca3f004ba874745a4087a89682617`: [generic stat layout](https://github.com/bminor/glibc/blob/9ea3686266dca3f004ba874745a4087a89682617/sysdeps/unix/sysv/linux/generic/bits/stat.h), [type widths](https://github.com/bminor/glibc/blob/9ea3686266dca3f004ba874745a4087a89682617/sysdeps/unix/sysv/linux/generic/bits/typesizes.h), and [xstat](https://github.com/bminor/glibc/blob/9ea3686266dca3f004ba874745a4087a89682617/sysdeps/unix/sysv/linux/generic/xstat.c). Their local reference copies are ignored, with respective SHA-256 `2414521352c40800e918a97a1bc71f82193dd2b2c9fa2344c55e8a26fd026dd8`, `eaef8263481fea098a1ef9bfd60d983e2498dd30438ce7924640327f5884dc3d`, and `147172a610cc7cb3bb56dfe3407c08b0c188b9f7cb4949c680ad77a43245da47`. The installed NDK's Android AArch64 `struct stat` layout is compile-time checked against selected sizes/offsets and values are copied field-by-field.

On an Android 15 x86-64 emulator using ARM64 translation, controls passed for regular file and descriptor metadata, symlink following, reserved buffer sentinels, unsupported version `EINVAL`, bad descriptor `EBADF`, missing file `ENOENT`, and unchanged result on failure. A synthetic library importing `__xstat@GLIBC_2.17` and `__fxstat@GLIBC_2.17` from `libutfileprobe.so` also passed. This does not validate every file type, filesystem, errno edge, glibc version, or physical ARM64 device. The test uses only app-private temporary files and removes them.

## Formatting experiment

`experiments/libc-probe/printf_probe.c` provides a restricted Bionic-`FILE*` formatting subset. Core-style wide output and selected narrow output passed expected-byte controls. Positional formats, long-double formats, and `%n` are deliberately rejected with `ENOTSUP`; this is a conservative behavior difference from glibc, not a complete implementation of its fortified checks. It only accepts Bionic-owned streams; glibc `FILE` layout, redirection, locale, concurrent state and all format combinations are not validated. A synthetic `__fprintf_chk@GLIBC_2.17` consumer also passed selected output and rejection checks.

## Incomplete libc-shaped candidate

`experiments/libc-probe` can build a test-only `libc.so.6` from the limited pthread, stat, C-locale, formatting and errno prototypes plus selected versioned ARM64 forwards for Bionic memory, wide strings, allocation, and Bionic-owned stdio. The selected stdio, memory, wide-string and allocator cases were exercised by a synthetic consumer. Test-only initial snapshots for `stdin`, `stdout`, `stderr` and `__stack_chk_guard` matched Bionic values in that consumer; dynamic reassignment, engine access to internal `FILE` layout and cross-runtime canary behavior are unverified. `environ` and `__environ` are intentionally absent rather than using a potentially stale snapshot.

`scripts/check_glibc_candidates.py` compares exact name, symbol version and ELF symbol type against Core's audited GLIBC imports. For the partial libc plus the test libm/libdl candidates, it reports **65 exact exported candidates and 64 missing out of 129**, status `INCOMPLETE` and exit code 1. This is a static name/version/type inventory: even its matching entries are not a validated ABI or engine-boot percentage. It does not cover C++/GCC imports, `ld-linux`, TLS, constructors, provider search rules, dynamic lookups, or behavior. The complete output is ignored `research/core-glibc-coverage.json`.

## Checked memory and formatting, 2026-11-03

The pinned original Core has `__sprintf_chk`, `__memset_chk`, and `__snprintf_chk` call sites at `0xf2330`, `0xf8a44`, and `0xfbd70` respectively. The first prepares a file-descriptor path with an 80-byte destination. These are static observations, not evidence that the paths execute on Android.

The isolated candidate now exports those three versioned functions. The memory wrapper checks the supplied object bound and calls `memset@LIBC` explicitly: an initial implementation called the NDK fortified inline `memset`, which compiled into a recursive call to the candidate's own `__memset_chk` and crashed the synthetic host. The explicit binding fixed this in the rerun. The formatting wrappers accept the same restricted format subset described above; they reject `%n` and other unsupported conversions, and are not full glibc replacements. The bounded `sprintf` path uses `vsnprintf` before aborting on overflow, so contents before process termination need not match glibc. `SIZE_MAX` denotes an unknown object size and cannot provide a bound.

The versioned synthetic consumer passed normal checked memory writes, a Core-style descriptor path, truncating `snprintf`, unknown-size `sprintf`, and unsupported `%n`. Three child-process checks separately observed `SIGABRT` for memory overflow, a requested `snprintf` size beyond the object, and overflowing `sprintf`. The earlier narrow/wide formatting regression also passed. These tests used the Android 15 x86-64 emulator with ARM translation, not an ARM64 device; expected aborts intentionally generate child crash diagnostics. The passing host log is `research/fortify-fixture.log` (ignored). No original engine library was loaded in the fixture.

To avoid accidentally treating it as a working libc, `scripts/run_partial_probe.ps1` stages this candidate and its synthetic test only under the debug app's `files/partial` directory; no `Core.so` is staged there. The separate `run_android_probe.ps1` continues to stage Core without this incomplete libc. On the translated emulator, the partial fixture passed its combined versioned errno, ctype, thread, stat, memory, allocation, stdio and fortified-narrow tests. The actual Core probe continues to fail at `libc.so.6`.
